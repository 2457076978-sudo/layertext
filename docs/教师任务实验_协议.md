# 教师任务实验 协议（阶段 4）

> 对应《LayerText 工程优化总计划》阶段 4：「然后做真实教师任务实验：**至少 3 位教师、同一章、相同任务**，
> 记录**首次成功、撤销、回退和完成时间**。」
> 验收标准：「教师实验能回答『**第一次点击是否成功**』和『**10 次操作后是否疲劳**』，而不是只报告模型输出指标」
>
> 代码在 `src/core/teacherexperiment.ts`，用法示例与断言在 `tests/teacherexperiment.test.ts`（24 条，含 3 组变异验证）。
> 这份文档只讲**人怎么做**，不讲代码怎么写的。

## 0. 它和「教师自助体检」不是一件事

`src/core/productmetrics.ts` 量的是**一位教师自己用**的时候顺不顺手，输入是他自己那份日志，输出是给他自己看的。
本协议量的是**一队人做同一件事**：同一章、同一份任务书、同一条成功判据，3 位教师各跑一遍。
所以两边的规矩不一样：自助体检里"还没有批量采纳"只是暂时答不上一个次要问题；
任务实验里**人数不够就不许有结论**——1 位教师跑出来的"第一次点击成功率 100%"不是发现，是一个人的一次经历被包装成结论。

## 1. 跑之前：先把任务书冻住（一次，5 分钟）

```ts
import { freezeTeacherTask } from './src/core/teacherexperiment.js';

const task = freezeTeacherTask({
  taskId: '第一章-A层-2026-09-20',
  chapter: '第一章',                                            // 与事件里的 chapter 逐字一致，不做模糊匹配
  segments: [{ id: 'P01', text: '…' }, { id: 'P02', text: '…' }], // 与风险队列同一套段号，逐段哈希
  tier: 'A',
  instruction: '把这一章的风险队列逐条过一遍：能采纳的采纳，不同意的退回，拿不准的标误报；过完点「我做完了」。',
  successCriterion: '队列里不再有待办（教师自认为处理完即可，不要求他判断 AI 对不对）。',
  frozenAt: '2026-09-20T09:00:00.000Z',                          // 冻结时刻由人给，本模块不读时钟
});
```

`task.hash` 就是这次实验的**身份证**：它只由「原文逐段快照 + 层级 + 指令逐字 + 成功判据」算出。
**换一句话指令、换一个层级、原文改一个词，指纹就变**——变了就不该把两批数放在一起比
（`taskDriftOf` 会逐项点名变的是什么）。`taskId` 和 `frozenAt` 不进指纹：编号是身份，不是输入。

冻完把它**原样发出去**，不要临场改。临场改的那句话，事后没人记得住。

## 2. 递给教师的四样东西

| # | 给什么 | 为什么 |
|---|---|---|
| ① | **逐字任务书**（`instruction`） | 三位教师拿到的必须**一个字不差**，否则跑的不是同一个任务 |
| ② | **成功判据**（`successCriterion`） | 让他知道"做到哪算完"，否则"完成率"这个词没有分母 |
| ③ | **同一章的同一份稿**（`chapter` + `tier`） | 计划明文要求同一章；层级不同，任务难度就不同 |
| ④ | **一个「我做完了」的按钮/一条口令** | 没有完成标记，完成与否只能靠待办条数推断，报告里会标成"推断" |

**不要给**：任何关于"这次是实验"的暗示、任何"这条 AI 建议对不对"的答案、任何让他放慢手速的要求。
要的就是他平时怎么点就怎么点——**第一次点击是否成功**和**10 次之后是否疲劳**只有在常态下才成立。

## 3. 当天，人要做的事

1. 每人一套环境、同一天内各跑一遍（跨天做，疲劳信号会被"隔了一夜"污染）；
2. 开跑前确认队列待办条数（打开队列会自动记一条 `session-open`，里面就带这个数）；
3. 全程**不打断、不提示、不解释**；他卡住了就记录下来，让他自己决定要不要继续；
4. 结束后记两件事：**谁来了**（名单 `roster`）、**谁没点几下就停了**；
5. 日志位置：`调适工作区/_决定/<层>.jsonl`（append-only，一行一条，只增不改）。

## 4. 跑完怎么出数

```ts
import { teacherExperiment, traceTeacherMetric, ALL_TEACHERS } from './src/core/teacherexperiment.js';
import { parseDecisionLog } from './src/core/decision.js';

const events = parseDecisionLog(logText).events;
const report = teacherExperiment({
  task,
  events,
  roster: ['教师甲', '教师乙', '教师丙'],
  currentTask: task,          // 再核一眼：跑完之后任务书有没有被改过
});

console.log(report.state, report.why);   // 未跑 / 教师数不足 / 有缺口 / 可出结论
report.verdict.forEach((l) => console.log(l));   // 直接抄进报告的那几行

// 任何一行数字，都能指回原始事件行：
traceTeacherMetric({ metric: '疲劳信号', teacherId: '教师乙' }, report);
traceTeacherMetric({ metric: '第一次点击是否成功', teacherId: ALL_TEACHERS }, report);
```

输出长这样（真跑出来是什么就印什么）：

- `✅ **第一次点击是否成功**：3 位教师里 2 位第一次点击就成功（67%），1 位第一次没成（撤销或系统没做成）`
- `⚠ **10 次操作后是否疲劳**：不给结论——只有 1 位教师做到了"第 11 次之后还有 ≥3 次决定"，计划要求**至少 3 位**`
- `完成情况：3 位里 3 位完成，完成用时中位数 18.0 分钟（其中 2 位是按待办条数推断的，不是完成标记）`

## 5. 结果怎么读（三条规矩）

1. **两个问题分开报，不许合成一个分**。报告上只有 `firstClick` 与 `fatigue` 两个并列字段；
   代码在报告出门前会跑 `assertSeparateQuestions`，有人塞一个"综合体验分"进去会直接抛错。
   "点不动"和"后段太累"是两件独立的事，合成一个数之后谁也拿不去做判断。
2. **先看 `state` 再读数**。`教师数不足` 表示这轮**没有发现**，只有过程记录；
   `有缺口` 表示某个问题单独证据不足——降级是**逐问题**的，别因为疲劳答不了就把上手数据也扔掉。
3. **一律说"算不出来"，不说 0**。没有一位教师的操作够到第 11 次，疲劳就是"算不出来"，
   **不是"不疲劳"**；完成用时没有依据就是 `null`，**不许填 0**。

## 6. ★ 这个实验**回答不了**什么

- **AI 的建议对不对**。系统没有真值。"第一次点击成功"的定义是**那一下点下去事情就办成了**
  （落定、且事后没被自己撤销），**不是**"AI 给的那条建议是对的"。
  想知道后者，只能事后请教师逐条回看——那是另一场实验，本协议不覆盖。
- **为什么不行**。这里只量"发生了什么"（撤销、回退、失败、多久做完），不回答"为什么"。
  原因得靠访谈，代码算不出来。
- **疲劳是不是真的让人点错了**。可见的是"后段撤销率上升"这个**代理信号**，
  它与"越点越随手"同向，但它**不是错误率**，更不能外推成"第 10 次之后 AI 会害人"。
- **3 位教师的结论能不能推广**。n=3 只够回答"在我们这儿，第一次点击到底顺不顺"，
  推不出"所有教师都会这样"。报告里任何一句话都不许写成"教师们普遍……"。
- **哪种 AI 策略更好**。这是四格实验（`src/core/experimentrun.ts`）的活。
  本实验里三位教师用的是**同一份稿**；换模型、换提示词，就换了一场实验。
- **成本和速度**。这里一个 token 都不数——那是模型输出指标，验收原话就是"而不是只报告模型输出指标"。

## 7. 还差什么才能真正拿到数字（已知缺口，如实列）

代码这一层已经能跑、能测、能追溯；**要拿到真数字，下面三件事必须由人在别的文件里补**（本轮不许改那些文件）：

1. **章节串必须逐字对齐**。事件里的 `chapter` 来自队列项（`app/src/risk.ts` 写决定事件时会带上它），
   本模块**只做逐字比对、不做模糊匹配**（模糊匹配会把"第一章"配到"第十一章"）。
   所以冻任务书时 `chapter` 要填队列里那一串原样字符；对不上的事件会被**排除出指标并点名**，
   而事件里干脆没记章节时，报告只会提醒"同一章这件事本轮无从核对"，不会拦。
2. **App 里没有「我做完了」这个按钮** → 完成与否只能靠 `session-open` 里的待办条数**推断**，
   报告里会标 `basis: 待办条数（推断）`。要"完成用时"是事实，就得有人写一条 `task-done` 事件
   （`taskDoneEvent()` 已经备好）。
3. **`session-open` 事件没有 `eventId` 字段**（`productmetrics.ts` 造的，落盘时也没补）→
   追溯靠按同一条规则现算兜底。想要原始日志那一行**自带**稳定 ID，得在写事件的那一步补上。

这三条都不影响本模块的行为与测试，但它们决定了"报告里哪些数是事实、哪些是推断"。
