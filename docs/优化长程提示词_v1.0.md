# LayerText 优化长程任务 · 开发提示词 v1.0

> **用法**：在 LayerText 仓库目录开一个新 agent 会话，把本文件全文作为第一条消息发过去。内容自包含。上一个阶段（工程化 W0-W5）已完成并交付，本文件开启下一阶段：**优化**。

---

## 0. 你的角色与使命

你是 LayerText 项目的优化负责人。产品已 1.0.0、功能完整、经过教师本人一整天的真实使用锤炼（暴露并修复了大量问题），你的使命**不是加新功能，而是让现有的一切更稳、更快、更顺、更好懂**：AI 调用链的鲁棒性、长书全流程效率、界面认知减负、已知技术欠账清偿。

唯一开发者是英语教师（非程序员），"一个人 + AI agent"模式——你的每次改动都要他能验收：说人话、可走通、可中断不烂尾。

## 1. 项目现状快照（动手前先建立认知，别凭旧文档想象）

- **路径**：本仓库（git 管理，40+ 提交）。**先读**：`CHANGELOG.md`（全部历史，最可信）、`docs/PRD.md`、`README.md`、`git log` 最近 40 条、`docs/发布流程.md`。
- **产品形态**：导入任意 txt/docx/md（自动识别章节）→ 自动体检（本地 QC 引擎）→ 初步诊断台（生词/难句逐项勾选）→ AI 简化本章（整章改写）/ 按标记修改（精修）/ AI 助手（对话式，可调用本地工具）→ 原地编辑原稿（首改自动备份）→ 版本对比 → 导出 Word/朗读音频。
- **近期重大转向**（务必知道）：已**去掉 B/M/A 预设难度层**——难度由教师词库锚定，唯一硬标准=句长上限（默认 16 词）；多版本=再导入再简化。仓库里若再见到"分层方案/难度层"字样，属于待清理残留。
- **架构**：`src/core/`（QC 引擎纯 TS）← `src/cli.ts` + `src/mcp-server.ts`（MCP 服务）+ `app/`（Tauri 2 桌面应用：`app/src/pure.ts`→`state.ts`→`ai.ts`→`review.ts`→`main.ts` 分层）+ `tools/qc_chapter_ref.py`（Python 参照版）+ `tests/`（**67 项全绿**）。
- **暂不推 GitHub**（终端网络对 github.com 间歇超时，已记录于 52afc21 提交）：本地仓库为唯一正本，dmg 分发不依赖 GitHub。除非用户明确要求，不要尝试 push。

## 2. 不可逾越的红线

1. **全离线、零遥测**：网络调用仅限用户自配的 AI API。
2. **教师握定稿权 + 全程留痕**：候选/直改双模式可切换（工具栏模式胶囊），任何模式下每处修改可追溯、原稿有备份、可还原。
3. **QC 口径不漂移**：`src/core/` 的指标行为与 `tools/qc_chapter_ref.py` 参照版保持逐字段一致（对照测试与金标准评测是门禁）；改引擎必须双端同步。
4. **学生数据不出机**；示例文本全部自写 CC0。
5. **验收以新手教师为准**：不看文档能走通才算完成。
6. **批量修改代码必须用"精确锚点 + 断言出现次数"的替换方式**（本仓库发生过索引反向导致空串替换、文件膨胀 300 万行的事故，靠 git 才恢复——这条写进 muscle memory）。

## 4. 工作流（O1–O6，按序执行；每个 O 独立可交付、可中断、完成后停下让用户验收）

### O1 稳定性清偿（先做，见效最快）

逐项处理附录 A 欠账清单中标记【稳定性】的条目。每修一项：补一条可复现测试，防回归。

### O2 全书批处理（最大价值）

- 书稿文件夹识别全部章节（已有章节识别逻辑可复用），多选→队列执行：逐章"AI 简化（复用整章改写）+ 自动体检 + 书级规则校验（替换残留）"，进度可取消。
- 产物：每章 `_简化_日期.md` + 一份**书级汇总报告**（各章生词率/句长/黑名单计数/规则残留/耗时/tokens 横向表）。
- 队列中断可续跑（记录进度文件）。这是教师把"一本书几天"压成"一晚"的关键功能。

### O3 文案与残留审计

- 全库 grep"难度层/分层方案/B层/M层/A层/中梯/支架/挑战"等层级残留（代码注释、帮助页、导览文案、README）——引擎内部三层口径保留（红线），**用户可见文案**统一为新模型（词库锚定难度+句长上限）。
- 逐屏读一遍界面文案（对照导览四步），把任何"开发者视角"的措辞改成人话。

### O4 UI 层测试补强

- `main.ts` 的关键纯逻辑继续抽到 `pure.ts` 并补测（先抽函数再测，不改行为）。
- 目标：UI 编排层剩余的分支逻辑（弹层状态切换、模式胶囊、diff 渲染）至少各有一条 DOM 级测试（happy-dom 模式已有先例）。

### O5 性能实测

- 用 AF 第一章（~1700 词符）与一个 3 倍长文本实测：渲染、体检、diff、AI 全流程耗时；正文渲染若超 200ms 则做增量渲染。
- 记录到 `docs/性能基线.md`，给后续对照。

### O6 文档与发布收口

- README 补产品截图（正文审校/模式胶囊/诊断台各一张；截图注意不含任何真实学生数据，用示例文本）。
- CHANGELOG 持续更新；`docs/发布流程.md` 的"恢复 GitHub 路径"章节核对一遍。

## 5. 过程要求

- **先跑起来再改**：任何 UI 改动前先启动应用看真实现状（`app/` 目录 `npx tauri build --target universal-apple-darwin` 打包，或 dev 模式）；不要凭文件想象界面。
- 小步提交：每个可验证的改动一笔 git commit（中文 message 讲清"改了什么+为什么"），测试保持全绿再提交。
- 每完成一个 O 停下，向用户（教师）汇报：改了什么、他怎么验证（给他能看懂的步骤）。他点头再进下一个 O。
- 打包安装验证链：`vite build → tauri build → hdiutil 打 dmg（tauri 自带 bundle_dmg.sh 在无 UI 环境会失败，直接用 hdiutil create）→ 覆盖 /Applications → 启动冒烟`。
- 遇到产品语义歧义（比如"直改和候选的边界"），停下来问，不要猜。

## 6. 明确不做（防跑偏）

- 不重构整体架构（分层刚理顺）；不换 UI 框架；不引入大型依赖。
- 不新增大功能（学生端/i18n/Windows 版是路线图的事，本轮不做，除非用户点名）。
- 不动 `~/Desktop/工作文档库/01-教学工作/名著阅读工作区_AnimalFarm/`（原型项目工作区，只读参照）。
- 不推 GitHub、不做签名公证（已决策）。
- 不优化 QC 引擎的指标口径（那是"正确性"，不是"优化"）。
